# 既存記録への影響確認（2026年11月10日）

結論：タブ・文言の整理による既存記録の削除はない。追加SQLも既存の記録を削除・置換しない。ただし、番号ログインと記録形式の変更までまとめて本番公開する場合は、以下の移行上の影響が残る。全利用者への影響がない状態として本番公開を承認できる段階ではない。

## 確認できたこと

- PGliteの独立したPostgreSQLへ架空の旧データを投入し、2つの移行SQLを順番に実行した。既存のAuth UUID・メール・パスワードハッシュ、プロフィール・選択習慣、todos、records、journals、admins、groupsの既存列、group_members、group_reports、posts、likes、comments、storage.objectsは実行前後で一致した。groupsへのkind列、別テーブルへの会員番号、新しい記録・歩み用テーブルを追加する構造。
- 画面テストで、本人のサーバー上の選択習慣と日別実施／スキップが新形式へ引き継がれ、以前の体重・メモ・日記が「記録レポート → 以前の体調記録を見る」で参照できることを確認した。
- ナビゲーションの変更は保存先を変えない。「みんなのご飯」は既存の写真投稿を残し、既存の7日間の公開期限を維持する。期限切れによる非表示は今回の変更で新たに追加された挙動ではない。
- 今回追加・更新した既存記録の検証を含め、関連13件が成功した。アプリの本番コードや本番データへの書き込みはこの確認では行っていない。

## 本番公開前に残る影響

1. 旧端末だけの記録：旧形式の所有者情報のないlocalStorageは保持するが、他人の記録の混入を防ぐため新アカウントへ自動移行しない。検証でも元の値が残る一方、新画面には出ないことを確認した。該当者のデータ保全・本人確認付き取り込み手順が必要。アプリのドメイン変更やブラウザーのデータ消去も避ける。
2. 既存利用者のログイン：Auth UUID・パスワードは維持するが、新画面では10桁の会員番号を求める。既存利用者への番号案内が済む前に切り替えると、ログアウト中の方は自力で入れなくなる可能性がある。
3. 以前の月次表示：新形式は本人の月間目標を分母にする。旧「月次まとめ」の手入力パーセンテージは自動変換しない。また、新形式へ取り込む習慣は現時点のprofiles.selected_habitsが対象で、以前だけ選んでいた習慣は新しい一覧に自動では加わらない。元のDBデータは残るが、新旧レポートが同じ表示になる保証はない。

## 本番データに関する未確認事項

この環境に本番の管理用接続設定はなく、実際の利用者データ・既存プロジェクトの制約や権限を照合していない。検証は架空データと画面の模擬接続によるもの。SQLの本番適用・公開ブランチへのマージ・デプロイは未実施。

公開前に、バックアップと検証環境を用意し、既存利用者の代表例で件数・値・ログイン・旧記録表示・新レポートを照合する。端末だけの記録の取り込み方法と会員番号の案内を整えてから、公開可否を判断する。
