# Bloom Journal：月間目標・番号ログインへの移行

## 実装内容

- 新規利用者はニックネーム、15文字以上のパスワードだけで登録。10桁のランダムな会員番号と192ビットの復旧コードを発行する。
- 本人のメール・本名は新規登録で収集しない。Supabase Authには会員番号由来の配信不能な `m<番号>@members.invalid` を内部識別子として使う。実在メールへの送信はしない。
- 既存利用者はAuthのUUID・パスワード・管理者権限を保持し、番号を追加する。既存Authにあるメールは、この移行で勝手に削除しない。
- 「できた／スキップ」「数値の月合計」「数値の月平均」「気分」のカスタム項目。日々の記録をスワイプすると、しずくが合わさって育つ。
- 月ごとの目標と、任意の月合計の手入力。実績 ÷ 目標 × 100を自動算出。手入力は日別合計への加算ではなく置き換え。0と未記録を区別する。超過達成は数字では100%以上を表示し、バーの描画だけを100%に収める。
- 日付を指定して複数項目をまとめて入力する欄も用意。習慣の「できた」は1日1回。1日に複数回数える場合は数値の項目を使う。
- 月次報告をSupabaseに保存し、管理者が番号とニックネームで確認・返信。利用者画面で返信を取得する。
- 既存のお知らせ、参加申請、グループ、ストーリー背景の操作を管理メニューに統合。イベントは既存groupsテーブルのkindで区分。
- 月次カードのPNG保存・端末の共有機能。既存ストーリー背景を使用し、番号とカウンセラーへのコメントは画像に含めない。

## 本番反映前の必須手順

1. Supabaseのバックアップを取得し、別プロジェクトまたはステージングで検証する。
2. Supabase SQL Editorで `supabase/migrations/202611090001_journal_v2.sql` を一度実行する。既存の `profiles`、`admins`、`groups` があるプロジェクトが対象。SQLはトランザクション内で適用される。
3. Vercelのサーバー環境変数に `.env.example` の4項目を登録する。`SUPABASE_URL` と `SUPABASE_ANON_KEY` はフロントの接続先と同じプロジェクトにする。`SUPABASE_SERVICE_ROLE_KEY` はサーバー専用で、HTMLや公開ファイルには絶対に置かない。
4. `AUTH_RATE_LIMIT_SECRET` は暗号学的乱数で32文字以上生成する。IPはHMACで匿名化してレート制限のキーに使用する。生のIP・パスワード・復旧コードはDBやログに保存しない。
5. 既存管理者でログイン済みの端末から移行を確認。管理画面で既存利用者の会員番号を確認し、本人確認済みの連絡経路で番号を案内する。ログアウト済みの既存利用者は、その番号と従来のパスワードで入る。
6. 既存利用者の初回認証時に復旧コードが一度表示される。コードとパスワードの両方を紛失した際の本人確認・運営窓口の手順を定める。番号だけを知る相手には復旧しない。
7. 新規登録、番号ログイン、復旧、端末切替、月次報告、管理者返信、既存グループ・お知らせ・画像共有をステージングで確認してから本番ブランチに取り込む。

新しいAPIは設定がない場合503で停止する。公開中のmainブランチには自動でマージしない。

現在のSupabaseのキー形式にも対応する。SUPABASE_ANON_KEYにはsb_publishable_形式、SUPABASE_SERVICE_ROLE_KEYには既存のsb_secret_形式を設定でき、従来のanon/service_role JWTも引き続き使用できる。新形式はapikeyヘッダーだけで渡し、利用者のアクセストークンは別のAuthorizationヘッダーに保持する。[Supabase公式のAPIキー仕様](https://supabase.com/docs/guides/getting-started/api-keys)に従う。変数名は既存設定との互換性のため維持する。

## わたしの歩み（2026年11月10日追加）

- 主ナビの体調記録を「わたしの歩み」に変更。既存データ・画面は維持し、「記録レポート」の「以前の体調記録を見る」から参照できる。
- 今日の自分を4つの選択肢から選択。コメントは任意の折りたたみ欄（160文字）。選択肢を選ばず自分の言葉だけで残すこともできる。日本時間の1日につき1件で、当日の内容を見直せる。
- 最初の公開範囲は自分だけ。本人がカウンセラーまたは承認済みグループを選んだ場合に限り共有する。グループは1投稿につき1つを明示選択。一般公開の選択肢はない。
- 線画アイコン付きの4つの応援は複数選択・取消が可能。同じ人の同じ応援が重複しない。コメントは400文字まで。送信IDにより再試行時の二重投稿を避ける。
- 「届いた応援」は自分への応援、「大切な言葉」は自分の歩みに他の人から届いたコメントを自動で集める。表示時と「最新の応援を読む」で更新する。プッシュ通知・リアルタイム配信は含まない。
- カウンセラーは管理画面の「歩み・応援」から共有された歩みを確認・返信できる。自分だけの投稿はカウンセラーにも見えない。「カウンセラーへ」は既存のadminsに登録された運営者に共有される。
- 投稿者は自分の歩みとそこへのコメントを削除できる。コメントを書いた本人・運営者も閲覧可能な投稿のコメントを削除できる。投稿の削除では関連する応援・コメントも削除する。
- 公開範囲・グループを変更する際は、以前の共有先から届いた応援・コメントを消すことを確認してから変更する。別グループへ以前のコメントを引き継がない。参加承認の取消後は該当グループの投稿を読めなくなる。
- 定期カウンセリングの予約は `https://timerex.net/s/iw-inc.jp/dd1d7f4f` を新しいタブで開く。個人情報・会員番号をURLに付加しない。「新規の方は別途お問い合わせが必要です。」を表示する。

### 追加の適用手順

1. 先の会員番号移行SQLの適用後、`supabase/migrations/202611100001_journey.sql` を適用する。既存のgroups（id/name）、group_members（group_id/user_id/status）、admins、member_identityが必要。承認済みの状態値は既存アプリに合わせてaccepted。グループIDはtextへ投影するため既存のUUID・数値のどちらも扱う。
2. 追加テーブルjourney_posts / journey_reactions / journey_commentsの直接アクセスは一般利用者・未ログインに許可しない。認証済みのjournal_journey RPCだけが、閲覧・投稿者・カウンセラー・グループ所属を検証して読み書きする。返却する著者情報はニックネームのみ。会員番号・認証UUID・メール・復旧コードはフィードに含めない。
3. assets/journey.jsとassets/journey.cssをindex.htmlとともに配信する。追加サーバー環境変数は不要。既存の番号ログイン用サーバー設定は引き続き必要。
4. ステージングで、2つの一般アカウントとカウンセラーにより共有・応援・コメント・公開範囲の変更・参加取消を確認する。既存プロジェクトのgroup_membersの承認操作が運営者だけに許可されていることも確認する。

一覧は自分の歩み50件・閲覧可能な他の人の歩み50件・届いたコメント100件までを直近順に表示する。他の人の投稿内のコメントは各20件まで。保存済みデータをこの件数で削除することはない。今回のSQLは適用用ファイルであり、作成だけでは本番データベースに適用されない。

### ナビゲーション・食事投稿の整理

- 「その他」を「記録レポート」に変更し、目標設定の次・わたしの歩みの前に配置。月次レポート・まとめ入力・以前の体調記録へ進む入口をまとめた。旧page-moreの内部IDはリンク互換のため保持する。
- タブの選択状態を表示順の配列番号から独立させ、各ページのキーで管理する。スマホは2段表示にし、主要な入口を横スクロールで探す必要をなくした。
- 「みんなの記録」は「みんなのご飯」に変更し、独立タブを追加。食事・外食・おやつの写真と任意のひとことを促す案内に変更した。既存posts・画像・いいね・コメントを移行・削除せず利用し、既存の7日間の公開期限も維持する。食事以外の画像を自動判定・ブロックする仕組みではない。レシピの長期保存や分類は今後の機能で、今回の7日間の投稿とは別に設計する。
- 右上の歯車でアカウント設定ダイアログを表示。会員番号・ニックネームの確認、ニックネーム変更、ログアウト、未ログイン時のログイン／登録へ進める。アカウント変更時は開いているダイアログを閉じ、以前の表示内容を消す。
- 投稿完了後のタブ切替がグローバルeventに依存して失敗していた箇所を修正した。
- この整理に新しいDB移行・サーバー環境変数は不要。写真のアップロード／投稿は既存のSupabase postsテーブルとpostsストレージの設定を引き続き使用する。

## データ移行・権限

- 新規テーブルは `member_identity`、`journal_workspaces`、`monthly_reports`、`report_replies`、`member_auth_limits`。会員番号・復旧ハッシュはサービスロール以外から直接読めない。
- 管理者APIは、毎回SupabaseでBearerトークンを検証し、既存adminsテーブルの所属を確認する。管理者フラグをクライアントから受け取らない。adminsへの一般ユーザーの書き込み権限をSQLで取り消す。
- 個人の記録・報告・返信の直接参照は本人だけ。管理者はサーバーで権限確認したAPIを使う。
- 日次の保存はブラウザー内に先に保管してから同期する。リビジョンが競合した場合は上書きを拒否し、端末の未同期分をバックアップしたうえでオンラインの記録を再読み込みできる。
- 新規ブラウザーの保存先はAuth UUIDごとに分離。既存単一HTMLのキャッシュも会員ごとに分離する。
- 最初の新形式の読み込み時、サーバーの本人のprofiles.selected_habitsとtodosを取り込む。旧端末の所有者情報のない共通localStorageは、他人のアカウントへの混入を防ぐため自動移行しない。元データは削除しない。
- 旧「月次まとめ」の手入力パーセンテージは、本人の月間目標を確認せずに回数へ逆算しない。切替前に、運営側で旧端末のみの未同期記録・旧月次手入力を持つ利用者を確認する。
- 以前の月の項目定義は月ごとに保持し、提出レポートには計算済みのスナップショットを保存する。新しい記録方法への変更は新IDを使い、過去の値の意味を変えない。

## 検証

`npm test` は計算・API・jsdomの画面操作と、PGlite上の実際のPostgreSQLによる移行・RLS・競合保存・復旧コード再使用防止を検証する。Supabaseの実Authサービス、実プロジェクトの既存RLS、実メール/ストレージ設定、端末のWeb Share APIはステージングでの確認が必要。

ローカルは `npm run dev`。サーバーAPIも試す場合は未追跡の `.env` を作り、`node --env-file=.env scripts/dev-server.cjs` を使う。設定なしでも、未ログインの端末内記録と新UIは確認できる。
